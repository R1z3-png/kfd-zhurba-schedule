# Лабораторная работа «Ничего не падает»

Консольное приложение на Kotlin/JVM читает расписание из UTF-8-файла, выбирает занятия по диапазону дат или типу и сообщает об ошибках отдельных строк. Команды, типы в файлах и диагностические сообщения — на английском языке. Отсутствующее значение обозначается обычным символом `-`.

Этот README описывает предоставленные исходники и тесты. Он не утверждает, что все требования защиты модели уже выполнены: известные ограничения перечислены ниже. Приведённые ожидаемые результаты получены чтением кода; запуск Kotlin и JUnit при подготовке документа не выполнялся.

## 1. Сборка и запуск

### Требования и доступная конфигурация

Нужны JDK 11 или новее (`Path.of` используется в чтении файлов) и Kotlin 2.0.20 или новее: в модели применяется `@ConsistentCopyVisibility`. Для удобства можно использовать JDK 17 и актуальный совместимый Kotlin.

В предоставленном наборе нет `build.gradle.kts`, `settings.gradle.kts` и Gradle Wrapper. Поэтому команды `./gradlew run` и `./gradlew test` нельзя считать готовыми командами существующего проекта. Ниже приведены независимая сборка приложения и вариант настройки Gradle для тестов.

### Сборка приложения через kotlinc

Если все исходники находятся в текущем каталоге, выполните:

```sh
kotlinc Cli.kt Commands.kt FailureMessages.kt FileLines.kt Main.kt Session.kt SessionParser.kt SessionRepository.kt AuditedSessionRepository.kt -include-runtime -d schedule.jar
```

Тестовые файлы в эту команду не включаются. При другом расположении исходников укажите соответствующие пути.

Запуск:

```sh
java -jar schedule.jar errors --file mixed.txt
java -jar schedule.jar period --file boundary.txt --from 2026-01-01 --to 2026-12-31
java -jar schedule.jar type --file teachers.txt --type EXAM
```

Путь с пробелами заключайте в кавычки. Основная JVM-точка входа — `schedule.MainKt`.

## 2. Формат файла и интерфейс команд

Каждая строка содержит ровно пять полей:

```text
date|type|topic|location|teachers
```

Примеры:

```text
2026-04-02|EXAM|Physics|Room 21|Alice,Bob
2026-04-03|LECTURE|Mechanics|Room 22|Alice
2026-04-04|PRACTICE|Problem solving|Room 23|Bob
2026-04-05|CANCELLED|Cancelled lecture|-|-
```

Правила:

- Дата записывается строго как `YYYY-MM-DD`, год — от 0001 до 9999; календарная дата должна существовать.
- Допустимы только `LECTURE`, `PRACTICE`, `EXAM`, `CANCELLED`, с точным соблюдением регистра.
- Все пять полей обязательны. Для отмены место и преподаватели записываются как `-`, а не как пустые поля.
- Тема, место действующего занятия и каждое имя преподавателя не могут быть пустыми, пробельными, содержать управляющие символы или внешние пробелы.
- Внутренние пробелы допустимы: `Room 21`, `Alice Smith`.
- Имена разделяются запятой без добавочных пробелов: `Alice,Bob`, а не `Alice, Bob`.
- У лекции и практики минимум один преподаватель, у сдачи — минимум два. Имена должны быть различными; сравнение регистрозависимое.
- У действующего занятия место и имена не могут быть `-`.
- В учебных примерах используются латинские имена, темы и места. Сам код не ограничивает текст только латиницей.
- Экранирование разделителей во входном формате не реализовано: `|` разделяет поля, а запятая — имена. Обратная косая черта не отменяет это правило.

Пробелы не удаляются автоматически. Неправильные данные отклоняются, а не исправляются.

### Команды

```text
period --file PATH --from YYYY-MM-DD --to YYYY-MM-DD
type --file PATH --type LECTURE|PRACTICE|EXAM|CANCELLED
errors --file PATH
```

Параметры можно переставлять. Неизвестные и повторные параметры, неверное число аргументов, пустые значения и значения, начинающиеся с `--`, отклоняются. Для файла с именем `--data` можно использовать путь `./--data`. Форма `--file=x` не поддерживается. Для `period` требуется `from <= to`.

- `period` включает обе границы диапазона и выводит дату, тип, тему и место, затем `Total: N`.
- `type` выводит также преподавателей, соединённых строкой `, `, затем `Total: N`.
- Для отмены `period` выводит одно поле `-` после темы, а `type` — два.
- `errors` выводит причины отклонения и итог `Rejected: K of N`.
- Сначала печатаются все ошибки файла, затем выбранные корректные занятия. Ошибки строк вне диапазона или другого типа тоже выводятся.
- Порядок занятий сохраняется как во входном файле; сортировки по дате нет.
- Форматированный вывод содержит пробелы вокруг ` | ` и не предназначен для повторной подачи в строгий входной парсер.

### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | Файл прочитан, отклонённых строк нет. Пустая выборка сама по себе не ошибка. |
| `1` | Есть отклонённые строки; корректные строки всё равно обрабатываются. |
| `2` | Неверные аргументы (`Invalid arguments`) или ошибка чтения (`Cannot read file`). |

Ошибки чтения `IOException`, `InvalidPathException`, `SecurityException` преобразуются в сообщение. Программные ошибки намеренно не подавляются общим `catch (Exception)`.

Файл читается в UTF-8, строки нумеруются с 1. LF и CRLF обрабатываются; пустая строка считается входной строкой и проверяется. Пустой файл содержит ноль строк. Reader закрывается через `use`.

## 3. Почему выбраны такие типы

### Доменная модель

`Session` — `sealed interface` с общими `date: LocalDate` и `topic: String`. Конкретные варианты:

| Класс | Тип в файле | Особенности |
| --- | --- | --- |
| `Lecture` | `LECTURE` | Место и минимум один преподаватель. |
| `Practice` | `PRACTICE` | Место и минимум один преподаватель. |
| `Assessment` | `EXAM` | Место и минимум два разных преподавателя. |
| `Cancellation` | `CANCELLED` | Только дата и тема; места и преподавателей в типе нет. |

У отмены нельзя задать противоречивое место или список: таких параметров у неё нет. Это защита устройством типа. Символы `-` относятся к формату файла и вывода, а не хранятся в `Cancellation`.

`sealed` задаёт закрытую иерархию для обработки вариантов через `when`. Наследование используется для общего контракта, а не для повторного использования изменяемого состояния.

`LocalDate` представляет календарную дату без ненужного времени суток. Но он допускает годы за пределами требований задания, поэтому ограничение `1..9999` дополнительно проверяется моделью.

Конкретные занятия — `data class`: автоматически доступны сравнение по значениям свойств (`equals`/`hashCode`), `toString` и компоненты для деструктуризации. Это удобно для тестов и хранения значений. Однако `data class` и `val` сами по себе не обеспечивают глубокую неизменяемость: список в `val` может оставаться изменяемым.

### Проверки при создании

Общие приватные функции проверяют дату, тему, место и преподавателей. Их вызывают блоки `init`, поэтому проверки действуют не только при чтении файла, но и при прямом создании объекта. Нарушение `require` приводит к `IllegalArgumentException`.

Порядок проверок конструктора не обязан совпадать с диагностическим приоритетом парсера: конструктор защищает инварианты, парсер выбирает одну понятную ошибку строки.

### Фабрика Assessment и copy

У `Assessment` приватный первичный конструктор. Публичный путь создания — `companion object` с `operator fun invoke`, поэтому запись выглядит привычно:

```kotlin
val exam = Assessment(date, "Physics", "Room 1", listOf("Alice", "Bob"))
```

Фабрика принимает `Collection<String>`, делает `toList()` и вызывает приватный конструктор, где выполняются проверки. Это отделяет список объекта от переданной изменяемой коллекции.

`@ConsistentCopyVisibility` делает сгенерированный `copy` согласованным по видимости с приватным конструктором. Это не просто подавление предупреждения: внешний вызов `exam.copy(...)` недоступен. Тем самым нельзя публично обойти копирование входного списка, вызвав сгенерированный `copy` с новым `MutableList`.

У `Lecture`, `Practice`, `Cancellation` конструкторы и `copy` публичные. `copy` снова вызывает конструктор и проверки `init`, но копирование поверхностное. У первых двух классов это не устраняет проблему изменяемого списка.

### Остальные типы

- `SessionType` — `enum class` для фиксированных обозначений команд и входного файла.
- `Command` — `sealed interface`, варианты команд — `data class`: после разбора набор параметров известен из типа команды.
- `SessionParseResult` — `sealed interface` с `Success` и `Failure`: ошибка данных является результатом разбора, а не исключением управления потоком.
- `SessionParseFailure` хранит структурированные причины; `FailureMessages.kt` независимо задаёт английский текст.
- `TextField` и `TeacherViolation` — перечисления фиксированных категорий ошибок.
- `AuditEvent` — `data class`, представляющий операцию и число добавленных элементов.
- `SessionRepository` — интерфейс хранения; `InMemorySessionRepository` — реализация в памяти; аудит добавляется композицией и делегированием.

`@JvmInline value class` в актуальных файлах не применяется. Поэтому утверждать, что тема, место или имя защищены отдельным value-типом, нельзя: сейчас это `String`, проверяемые при создании занятия.

## 4. Защита коллекций: что действительно гарантировано

### Входной список

`Assessment` копирует переданную коллекцию через `toList()`. Поэтому последующее `clear`, `add` или изменение элемента исходного `MutableList` не изменяет список сдачи. Элементы — строки, поэтому отдельного глубокого копирования объектов преподавателей здесь не требуется.

`Lecture` и `Practice` сохраняют переданный `List` напрямую. Передача `MutableList` оставляет внешнюю ссылку на то же хранилище. После успешной проверки можно очистить список и получить действующее занятие без преподавателей. Это незакрытый обход публичного API.

### Выданный список

`List<String>` — интерфейс только для чтения, а не гарантия физически неизменяемого объекта. Через обычную переменную такого типа нельзя вызвать `clear`, но приведение к `MutableList` может открыть изменяемый объект.

В `Assessment` свойство `teachers` возвращает сохранённую копию напрямую. Для списка из нескольких элементов результат `toList()` на Kotlin/JVM обычно является изменяемым хранилищем за read-only интерфейсом. Защитной обёртки или нового снимка при каждом чтении нет. Поэтому защита от исходного списка присутствует, а гарантированной защиты от изменения через выданный список — нет.

### Репозиторий и аудит

`InMemorySessionRepository.all()` возвращает `sessions.toList()`, а `auditEvents` — `auditLog.toList()`. Это независимые снимки: изменение структуры полученного снимка не меняет внутреннюю коллекцию, а последующие добавления не меняют старый снимок.

Но снимок репозитория поверхностный: объекты занятий остаются теми же. Уязвимость списка преподавателей внутри занятия не исчезает из-за копирования списка занятий.

Для выполнения строгого требования «нельзя испортить через публичный API» нужно защитить вход и выход коллекций у всех действующих занятий. Возможные решения — приватная копия и выдача отдельных снимков либо защитная неизменяемая обёртка над собственной копией. В текущем коде это ещё не реализовано полностью.

## 5. Попытки сломать модель

Следующие случаи относятся к прямому API, а не только к парсеру. В примерах:

```kotlin
val date = LocalDate.of(2026, 10, 12)
```

### 1. Создать занятие с пустой темой

```kotlin
Assessment(date, "", "Room 1", listOf("Alice", "Bob"))
Assessment(date, "   ", "Room 1", listOf("Alice", "Bob"))
```

Оба создания отклоняются с `IllegalArgumentException`. Защита: проверка `isNotBlank()` при создании; это не свойство типа `String`. Существующий тест: `blankTopicRejected`.

### 2. Создать занятие с годом 0 или 10000

```kotlin
Assessment(LocalDate.of(0, 1, 1), "Physics", "Room 1", listOf("Alice", "Bob"))
Assessment(LocalDate.of(10000, 1, 1), "Physics", "Room 1", listOf("Alice", "Bob"))
```

`LocalDate` позволяет представить такие годы, но конструктор занятия отклоняет их через `require(date.year in 1..9999)`. Защита: проверка при создании. Существующий тест: `yearOutOfRangeIsRejected`.

### 3. Создать действующее занятие без преподавателей

```kotlin
Assessment(date, "Physics", "Room 1", emptyList())
Lecture(date, "Physics", "Room 1", emptyList())
Practice(date, "Physics", "Room 1", emptyList())
```

Все три создания отклоняются: минимумы равны 2, 1 и 1 соответственно. Непустой список пустых строк тоже недопустим. Защита: проверки количества и элементов при создании. Существующий `emptyTeachersList` проверяет `Assessment`; варианты с `Lecture` и `Practice` — дополнительные примеры, не отдельные существующие тесты.

### 4. Создать сдачу с одним преподавателем

```kotlin
Assessment(date, "Physics", "Room 1", listOf("Alice"))
```

Создание отклоняется. Список `listOf("Alice", "")` тоже отклоняется, но уже проверкой пустого имени после проверки размера. Защита: проверки при создании. Существующий тест: `oneTeacherInAssessment`.

### 5. Создать сдачу с двумя одинаковыми преподавателями

```kotlin
Assessment(date, "Physics", "Room 1", listOf("Alice", "Alice"))
```

Создание отклоняется проверкой `teachers.distinct().size == teachers.size`. Защита: проверка при создании, а не использование `Set` (в API остаётся список). Существующий тест: `twoSameTeachersInAssessment`.

### 6. Изменить исходный список после создания занятия

```kotlin
val names = mutableListOf("Alice", "Bob")
val exam = Assessment(date, "Physics", "Room 1", names)
names.clear()
check(exam.teachers == listOf("Alice", "Bob"))
```

Для `Assessment` инварианты сохраняются благодаря копированию в фабрике. Существующий тест: `clearedNamesKeepsAssessment`.

Контрпример для текущей реализации:

```kotlin
val names = mutableListOf("Alice")
val lecture = Lecture(date, "Physics", "Room 1", names)
names.clear()
check(lecture.teachers.isEmpty()) // Модель уже испорчена.
```

Аналогично уязвима `Practice`. Здесь проверки при создании недостаточно: нужна защита коллекции на входе. Контрпример не включён в приложенный набор тестов.

### 7. Изменить состояние занятия через выданный список

Обычный вызов `exam.teachers.clear()` не компилируется, поскольку тип свойства — `List<String>`. Но этого недостаточно для полной защиты.

Дополнительная проверка для Kotlin/JVM:

```kotlin
val exam = Assessment(date, "Physics", "Room 1", listOf("Alice", "Bob"))
val exposed = exam.teachers as MutableList<String>
exposed.clear()
check(exam.teachers.isEmpty()) // При изменяемом backing list инвариант нарушен.
```

Текущее устройство не гарантирует запрета такой мутации. Нужна защита выдаваемой коллекции, а не повторный `require` только при создании.

Существующий `returnedTeachersListKeepsAssessment` только получает `List<String>` и сравнивает его содержимое. Он не вызывает мутирующих операций и не доказывает устойчивость к приведению типа. Пример выше — дополнительная проверка, не выполненный JUnit-тест в предоставленном наборе.

### 8. Обойти проверки через copy

```kotlin
// Не компилируется снаружи Assessment: copy приватный.
// exam.copy(teachers = mutableListOf("Alice"))
```

Защита `Assessment`: устройство API — приватный конструктор, фабрика и `@ConsistentCopyVisibility`. Такой случай нельзя проверять обычным runtime `assertFailsWith`: ошибка возникает при компиляции.

Для публичных `copy` других занятий:

```kotlin
val lecture = Lecture(date, "Physics", "Room 1", listOf("Alice"))
// Бросает IllegalArgumentException: init выполняется повторно.
lecture.copy(topic = "")
```

Проверки сохраняются, но коллекции копируются поверхностно:

```kotlin
val names = mutableListOf("Alice")
val copied = lecture.copy(teachers = names)
names.clear()
check(copied.teachers.isEmpty()) // Уязвимость Lecture остаётся.
```

Для `Cancellation.copy(topic = "")` также выполняется проверка конструктора; списков у этого типа нет. Отдельных тестов `copy` в предоставленных файлах нет.

### Сводка механизмов

| Попытка | Механизм защиты / состояние |
| --- | --- |
| Пустая тема | Проверка при создании. |
| Год 0 или 10000 | Проверка при создании сверх возможностей LocalDate. |
| Нет преподавателей | Проверка при создании, но возможна последующая мутация списка. |
| Один преподаватель у сдачи | Проверка при создании. |
| Два одинаковых имени | Проверка при создании. |
| Изменить исходный список | Защита коллекции только у Assessment; у Lecture/Practice не закрыто. |
| Изменить выданный список | Read-only тип ограничивает обычные вызовы, но полной защиты коллекции нет. |
| Обойти через copy | У Assessment метод скрыт устройством API; у остальных init проверяется повторно, но списки остаются уязвимы. |

## 6. Делегирование и аудит репозитория

```kotlin
class AuditedSessionRepository(
    private val delegate: SessionRepository,
) : SessionRepository by delegate
```

Делегирование перенаправляет непереопределённые методы интерфейса объекту `delegate`. Это композиция, а не наследование от реализации репозитория.

### Почему недостаточно переопределить только add

`add` и `addAll` — разные публичные методы. Если обёртка переопределяет только `add`, вызов `wrapper.addAll(...)` перенаправляется непосредственно в `delegate.addAll(...)` и не проходит через `wrapper.add(...)`.

В текущем `InMemorySessionRepository.addAll` вызывается `sessions.addAll(newSessions)`. Вызовов `add` обёртки вообще нет. Даже если бы делегат внутри `addAll` вызывал собственный `add`, получателем был бы делегат, а не внешняя обёртка. Делегирование не перехватывает внутренние вызовы автоматически.

Поэтому `AuditedSessionRepository` явно переопределяет оба метода:

- `add(session)` вызывает делегат, добавляет одно событие `AuditEvent("add", 1)` и увеличивает `totalAdded` на 1.
- `addAll(sessions)` вызывает делегат, добавляет одно событие `AuditEvent("addAll", sessions.size)` и увеличивает счётчик на размер входа.
- `addAll(emptyList())` тоже регистрирует один вызов, но с `count = 0`.
- `all()` делегируется и не создаёт событий.

Событие добавляется после успешного возврата метода делегата. Это аудит успешных вызовов через обёртку, а не всех попыток и не прямых обращений к внутреннему репозиторию. Изменения через сохранённую внешнюю ссылку на `delegate` не учитываются. CLI сейчас собирает занятия в списки напрямую и не подключает `AuditedSessionRepository`.

Дубликаты занятий в репозитории допустимы; счётчик учитывает все переданные элементы, а не число уникальных занятий. В `AuditedSessionRepositoryTest` проверяются одиночное добавление, пакет из трёх элементов, пустой пакет и отсутствие события при `all`.

## 7. Приоритет ошибок парсера

На одну строку возвращается ровно одна ошибка — первая по следующему порядку. После отказа более поздние этапы не выполняются.

1. Нет символа `|` — неверный разделитель.
2. Число полей не равно пяти.
3. Пустое или полностью пробельное поле — первое в порядке `date`, `type`, `topic`, `location`, `teachers`.
4. Неверный формат или значение даты, включая недопустимый год.
5. Неизвестный тип занятия.
6. У `EXAM` менее двух подходящих элементов списка преподавателей.
7. Остальные нарушения домена, в следующем порядке:
   1. Управляющие символы.
   2. Внешние пробельные символы.
   3. Неверные поля отмены: сначала место, затем преподаватели.
   4. Место `-` у действующего занятия.
   5. Недопустимые элементы списка преподавателей — по порядку элементов.
   6. Повторные имена преподавателей — первое повторно встретившееся имя.

На этапах управляющих символов и внешних пробелов поля также обходятся в порядке `date`, `type`, `topic`, `location`, затем имена преподавателей слева направо. При этом более ранние этапы имеют преимущество: например, пробелы в дате дадут `invalid date`, а не сообщение о внешних пробелах.

### Важная точность этапа EXAM

В текущем коде на этапе 6 подсчитываются элементы, которые одновременно:

- не пустые и не полностью пробельные;
- не равны `-`;
- не имеют внешних пробелов;
- не содержат управляющих символов.

Это строже буквального требования считать только непустые/непробельные элементы, отличные от `-`. Например, `Alice, Bob` даёт `got 1` ещё до этапа внешних пробелов. Если требуется буквально исходный приоритет только с тремя условиями подсчёта, нужно изменить код этапа 6; README сам этого расхождения не устраняет.

Повторы на этапе 6 не удаляются: `Alice,Alice` содержит два подходящих элемента и доходит до ошибки `duplicate teacher`. Несмотря на имя класса `TooFewDistinctTeachers`, поле `actual` в текущем коде — не число уникальных имён. Уникальность проверяется отдельно в конце.

Примеры конкурирующих нарушений:

| Вход | Выбранная причина |
| --- | --- |
| `bad line` | Нет разделителя. |
| `2026-01-01|LECTURE` | Неверное число полей. |
| `|LECTURE|Topic|Room 1|Alice` | Пустое поле date, а не неверная дата. |
| `2026-13-45|SEMINAR|Topic|Room 1|Alice` | Неверная дата, а не неизвестный тип. |
| `2026-01-01|EXAM| Topic|Room 1|Alice` | Недостаточно преподавателей, а не пробел в теме. |
| `2026-01-01|EXAM|Topic|Room 1|Alice,Alice` | Повторное имя, а не недостаток преподавателей. |

В `SessionParserTest` уже проверяются пустая дата перед неверной датой, неверная дата перед неизвестным типом и диагностика двух одинаковых преподавателей. Это не полное покрытие всех сочетаний приоритетов.

## 8. Сообщения об ошибках

Полная диагностика имеет вид `line N: REASON`, где `N` — номер строки с 1. Значения из входных данных экранируются: обратная косая черта как `\\`, кавычка как `\"`, символы вне печатного ASCII — как `\uXXXX` с шестнадцатеричными цифрами в нижнем регистре. Это формат диагностики, не синтаксис входных файлов.

### Основные причины

```text
line N: invalid field separator
line N: got K fields, expected 5
line N: empty required field "date"
line N: invalid date "2026-13-45"
line N: unknown session type "SEMINAR"
line N: type "EXAM" requires at least 2 teachers, got K
```

Для пустого поля вместо `date` выводится одно из `date`, `type`, `topic`, `location`, `teachers`.

### Остальные нарушения домена

```text
line N: topic must not contain control characters
line N: topic must not have leading or trailing whitespace
line N: type "CANCELLED" requires location "-"
line N: type "CANCELLED" requires teachers "-"
line N: location must not be "-"
line N: teacher #1 must not be blank
line N: teacher #1 must not be "-"
line N: duplicate teacher "Alice"
```

В сообщениях об управляющих символах и внешних пробелах вместо `topic` выводится имя соответствующего поля. Для преподавателей текущий formatter печатает именно:

```text
line N: teachers must not contain control characters
line N: teachers must not have leading or trailing whitespace
```

Хотя структурированная причина хранит `teacherIndex`, ветки `ControlCharacter` и `OuterWhitespace` в `formatFailureReason` его сейчас не используют. Приватные функции `controlCharacterMessage` и `outerWhitespaceMessage`, которые умеют выводить `teacher #N`, определены, но не вызываются.

Для `InvalidTeacher` также предусмотрены тексты:

```text
line N: teacher #1 must not have leading or trailing whitespace
line N: teacher #1 must not contain control characters
```

Однако при обычном разборе строки такие нарушения перехватываются более ранними общими этапами, поэтому эти варианты formatter доступны для структурированной причины, но обычно не достигаются из `parseSessionLine`. Полностью пробельный элемент с внешними пробелами также может быть отклонён раньше как нарушение внешних пробелов; пустой элемент внутри непустого списка доходит до `teacher #N must not be blank`.

Индексы в сообщениях парсера начинаются с 1. Сообщения прямых `require` модели — отдельный слой: например, `Topic must not be blank`, `Year must be in range 1..9999`, `Teacher names must be distinct`; для имён модель использует индекс с 0.

## 9. Собственные файлы для проверки из консоли

Здесь описаны только `mixed.txt`, `boundary.txt`, `teachers.txt`. Остальные учебные TXT-файлы намеренно не рассматриваются. Все блоки ниже — ожидаемый вывод приложения по текущим исходникам.

### mixed.txt: корректные и ошибочные строки вместе

В файле семь строк: четыре корректные, три отклоняемые. Проверяется, что ошибки не мешают выборке корректных занятий и что ошибка вне диапазона тоже выводится.

```sh
java -jar schedule.jar period --file mixed.txt --from 2026-03-02 --to 2026-03-05
```

```text
line 2: invalid field separator
line 4: invalid date "2026-02-30"
line 7: invalid date "2026-13-40"
2026-03-02 | PRACTICE | Valid practice in filter | Room 11
2026-03-05 | CANCELLED | Cancelled in filter | -
Total: 2
```

Код завершения: `1`.

```sh
java -jar schedule.jar errors --file mixed.txt
```

```text
line 2: invalid field separator
line 4: invalid date "2026-02-30"
line 7: invalid date "2026-13-40"
Rejected: 3 of 7
```

Код завершения: `1`.

### boundary.txt: включённые границы диапазона

Все пять строк корректны. Первая и последняя даты диапазона должны включаться, две даты за его пределами — исключаться. Отмена внутри диапазона тоже выбирается.

```sh
java -jar schedule.jar period --file boundary.txt --from 2026-01-01 --to 2026-12-31
```

```text
2026-01-01 | LECTURE | First boundary | Room 1
2026-12-31 | EXAM | Last boundary | Room 3
2026-06-01 | CANCELLED | Cancelled lecture | -
Total: 3
```

Код завершения: `0`. Июньская запись выводится после декабрьской, поскольку сохраняется порядок файла, а не хронологическая сортировка.

### teachers.txt: преподаватели и отмена

Из шести строк корректна только сдача с двумя разными преподавателями.

```sh
java -jar schedule.jar type --file teachers.txt --type EXAM
```

```text
line 1: type "EXAM" requires at least 2 teachers, got 1
line 3: duplicate teacher "Alice"
line 4: teacher #2 must not be "-"
line 5: type "CANCELLED" requires location "-"
line 6: type "CANCELLED" requires teachers "-"
2026-04-02 | EXAM | Two teachers | Room 21 | Alice, Bob
Total: 1
```

Код завершения: `1`. Команда `errors --file teachers.txt` выведет те же пять ошибок и итог `Rejected: 5 of 6`.

## 11. Текущий итог по требованию защиты модели

Проверки корректности при создании вынесены в модель и не зависят от парсера. Отмена защищена отсутствием неприменимых полей. Assessment дополнительно копирует входную коллекцию и скрывает copy. Репозиторий и аудит возвращают снимки своих коллекций. Аудит явно учитывает оба метода добавления.

Но полное требование невозможности испортить объект через публичный API пока не выполнено: Lecture/Practice сохраняют внешние списки, а Assessment выдаёт внутренний список без гарантированной неизменяемой защиты. Также этап подсчёта преподавателей EXAM строже буквального требования о приоритете ошибок. Эти ограничения должны исправляться в коде и закрепляться отдельными тестами, а не скрываться формулировками README.
